## 5. New finding from my own probe: the **middle** coordinate has the same defect

The instruction asked whether the middle coordinate — the `levelPointN` denominator, `hPc`/`hPij` in the payloads —
can vanish in general position. I probed it (`r10_jack/midcoordinate_probe.py`), minimising that cross-vector
coordinate over random families and checking `GenPosN` (all pairs `Transversal`, all triples `triP`/`cycP`), and used
`n = 4` as a **built-in sanity test**, because r9 proved `crossVec_KP4_P2_ne_zero` from `GenPos4` in Lean:

| `n` | middle index | result |
|---|---|---|
| 4 | 2 | **no** `GenPosN` solution (|v| → 4.5e-15 but the margin collapses) — agrees with the Lean theorem ✓ |
| **6** | 3 | **`GenPosN` holds with the coordinate `= 0`** (|v| = 6.0e-16, general-position margin 0.018) |
| 8 | 4 | undecided — no `GenPosN` solution found in 6 searches |

An earlier version of this probe used the wrong `cycP` (real `[[x, yx, y]]` instead of Lean's complex
`[[c, c̄c, c̄]]`) and reported a fake `n = 4` solution; the `n = 4` sanity test is what caught it. The table above is
the corrected probe.

**And it is exact, not just numeric.** The same radial trick as r9 gives six Gaussian-rational centres with the
middle coordinate vanishing exactly (`r10_jack/mid_zero_exact.py`):

```
c6 = (-89/50, -178/75), (-745/338, -894/169), (-1189/578, -17835/4624),
     (-2929/1250, -35148/4375), (-2605/1682, -10941/6728), (-8081/3362, -161620/15129)

crossVec (KP 6 c6 c̄) ⟨3⟩ = 0  exactly;   min Transversal 1.562, min triP 0.272, min cycP 3.590
```

Construction: the six centres lie on the curve `x y² + x² y − y² + 3xy − x² = 0` (with `y = x̄`), which is exactly the
column relation `(0, −1, 1, 1, 3, 1)` among the columns `[y³, −xy², x²y, −y², xy, −x²]` of `KP 6 c c̄` with column 3
dropped; it is parametrised by `z = r e^{iθ}` with `r = (2cos2θ − 3)/(2cosθ)`, so Pythagorean directions keep every
coordinate rational. (First two attempts failed for instructive reasons: treating `(x, y)` as real coordinates rather
than `(c, c̄)`, and letting the radial parameter `r` be complex while substituting `ȳ = r e^{−iθ}` as if it were real.)

**Why this matters.** At `k = 0`, `heven_levelPoint`'s `hPc` is exactly that coordinate (`crossVec (KP 6 c c̄) ⟨3⟩`),
so it is **not** derivable from `GenPosN` either — the same dead end as `hP0`, at the other end of the vector. And
this one is worse in kind: when it vanishes, `levelPointN 6` divides by zero, so `Ept 6 c` is the junk value `0`
rather than the point it should be. Projectively the level point is `[−v_last : v_{n/2}]`, so the correct total
definition is

```lean
Ept∞ n c := if v ⟨n/2⟩ = 0 then ∞ else ↑(−v_last / v ⟨n/2⟩)      -- v = crossVec (KP n c c̄)
```

which is the **same phenomenon** as `P₀ = 0`: in ℂP¹ the level points are concyclic-with-∞ exactly when they are
collinear. One geometric statement covers both degeneracies; `Ept` as defined in r9 does not.

`hodd_levelPoint`'s `hPi` is the subfamily middle coordinate at `n = 2k+4`, i.e. `n = 6` at `k = 1` — so both
payloads are affected, not just `heven`.
